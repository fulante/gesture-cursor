## 摘要

Gesture Cursor 用普通摄像头和 MediaPipe 手部关键点，把手指动作映射为鼠标操作：
移动、单击、双击、拖拽、右键、滚动和系统音量。所有视频都在本地处理，不上传
云端。

项目从一个“能跑的 demo”开始，经过六个版本迭代，逐步解决了真实使用中暴露的
问题：

- 手势阈值随距离/分辨率漂移；
- 右键在“拇指自然贴中指”时误触；
- 滚动状态显示正确但页面不动；
- 光标偶发冻结；
- 关闭按钮左键偶尔没反应；
- 缺少双击；
- 缺少不离开手势模式的音量控制；
- PyAutoGUI 安全角触发时左键可能卡住；
- 相机实际分辨率未被采用，光标映射偏移；
- 手离开活动区域后光标贴边/像卡住。

当前 v1.1.5 已实现完整鼠标词汇、音量控制，并修掉相机实际分辨率映射和
failsafe 按键释放问题，**38 个自动化测试通过**；用户已验收稳定性、滚动、
右键和左键修复，双击、音量和安全角/分辨率在阈值/手感上等待最终真机确认。
仍待产品化的主要问题是：摄像头管理员权限、端到端延迟测量、DPI/多屏和安装包。

## 一、产品定义

### 1.1 背景与目标

参考项目本身已经具备 MediaPipe 手部跟踪、PyAutoGUI 鼠标控制和基本状态机。
本项目的工作重点不是“再写一个手势识别 demo”，而是把它变成一个**在真实桌面上
连续使用也不容易出错**的产品原型。

目标：

1. 不增加额外硬件，普通笔记本摄像头可用；
2. 本地运行，不上传视频；
3. 手势可学习、单手完成；
4. 出错时能恢复，不能把光标卡死；
5. 每个改动可验证、可回滚、可记录。

### 1.2 目标场景

- **演示/教学**：演讲时远离键盘，用手势翻页、移动光标；
- **无障碍**：手部操作受限、无法稳定使用触摸板的人群；
- **无接触/卫生场景**：公共终端、医疗/实验室等不希望触摸设备的环境；
- **多任务**：双手被占用时临时控制光标。

当前产品仍是原型，尚未针对某一场景做正式用户研究；产品介绍时应先选一个主场景，
不要把“所有人都能用”作为卖点。

### 1.3 成功标准

- 手势误触率、单击/双击成功率；
- 光标跟手程度、端到端延迟；
- 光标不冻结、不粘滞；
- 右键/滚动/拖拽等动作边界清楚；
- 用户能在 1 分钟内学会基本手势；
- 换一台电脑/摄像头仍能运行。

## 二、基线版本：为什么“能跑”不等于“能用”

### 2.1 环境基线

最初项目依赖 Python 3.12 和 `mediapipe==0.10.21`。本机实际可用的是 Anaconda
Python 3.13，而 mediapipe 0.10.21 没有 cp313 wheel；旧 3.11/3.12 注册项也已失效。
因此我们先部署了项目内 CPython 3.12.8、虚拟环境和固定依赖，保证可复现。

摄像头方面，AI 会话是 Low 完整性级别，Windows 拒绝打开摄像头；用户以管理员
身份运行后可用。这一点后来成为产品化的 P0 问题，而非“环境小问题”。

### 2.2 初始手势实现

初始版本的手势状态机：

- 手指是否伸出：用 `tip.y < pip.y` 判断；
- 捏合/右键：固定像素阈值 `40 px`；
- 滚动：硬死区 + 锚点重置 + 整数截断；
- 右键：电平触发，按住会反复右键；
- 捏合→拖拽：只看时间。

这些实现适合演示，但真实使用时暴露出系统性问题。

### 2.3 第一轮真实体验

用户实际使用后反馈：

- 滚动、右键“不灵敏”，有时不触发、有时误触、有时连续右键；
- 拇指只是自然贴在中指上，也会莫名右键；
- HUD 显示 `SCROLL`，上下移动手却不滚；
- 光标有时停在一个区域，过一会才恢复；
- 移动到关闭按钮后左键有时没反应；
- 没有双击。

### 2.4 为什么不是“调一下阈值”？

因为问题不是单个阈值大小，而是：

1. **几何不可迁移**：固定像素阈值会随手距、分辨率变化；
2. **手指判定只看 y**：手一倾斜就失效；
3. **手势优先级冲突**：右键被捏合/滚动抢；
4. **触发模型错误**：静止接触被当成右键，时间到了就被当成拖拽；
5. **缺少状态超时**：锁存/捏合可能长期阻断光标；
6. **系统集成错误**：Windows 滚轮单位错误导致“触发了但没效果”。

因此我们采用“每次只解决一个用户可见失败模式”的迭代方式，而不是继续堆手势。

## 四、迭代一（v1.1.0）：把“像素手势”变成“尺度无关手势”

### 4.1 为什么迭代

滚动和右键在真实使用中不稳定。用户无法依赖“有时能用”的手势完成日常操作，
这是从 demo 走向产品的第一道门槛。

### 4.2 用户体验

- 右键有时触发、有时不触发；按住还会连续右键；
- 滚动要么不动，要么一下跳很多格；
- 手稍微倾斜、离摄像头远一点，手势就变了；
- HUD 显示的状态和实际动作对不上。

### 4.3 根因

- 所有阈值是固定像素，手距/分辨率一变就漂移；
- 手指伸展用 `y` 比较，手倾斜就失效；
- 右键要求“中指伸直”，与“中指去碰拇指”的动作矛盾；
- 捏合、滚动、右键的优先级互相抢；
- 右键电平触发，按住会重复；
- 滚动用硬死区 + 锚点重置 + 整数截断，慢速移动被丢弃，快速移动跳跃。

### 4.4 如何改进

- 用 **手掌尺寸**（wrist → middle MCP）归一化所有距离；
- 手指伸展改为“指尖到 MCP / PIP 到 MCP 距离 + PIP 关节角”，并加迟滞；
- 右键改为边沿触发 + 锁存，允许中指弯曲；
- 滚动改用手掌中心 + 小数累加器 + 每帧限幅 + 0.18 秒宽限期；
- 所有鼠标动作捕获 PyAutoGUI failsafe；
- 引入合成关键点测试，先保证状态机逻辑可回归。

### 4.5 结果

17 个测试通过。用户反馈右键“足够灵敏了”，但出现了静止拇指误触和滚动不动的
新问题——这推动进入迭代二。

**产品表达**：从“能演示”到“能稳定用”，手势不再依赖固定像素。

## 五、迭代二（v1.1.1）：让右键和滚动真正“跟手”

### 5.1 为什么迭代

用户正常伸食指移动光标时，拇指会自然贴合中指，触发莫名右键；同时 HUD 显示
`SCROLL`，但上下移动手页面不动。两个问题都直接影响基本操作。

### 5.2 用户体验

- 移动光标时突然右键，打断操作；
- 两指滚动姿势被识别，但页面完全不动；
- 不确定是手势没触发，还是触发了但系统没收到。

### 5.3 根因

- 右键只判断“拇指-中指距离小”，静止贴合也被当成右键；
- 右键候选在滚动之前 `return`，静止拇指会抢占滚动帧；
- 滚动死区/每格距离偏大，小幅移动被吞掉；
- **PyAutoGUI 0.9.54 的 Windows `_scroll` 把格数直接作为 `mouse_event` 的
  `dwData`，而 Windows 需要 `WHEEL_DELTA=120`**；`scroll(1)` 实际只有 1/120 格，
  页面几乎不动。

### 5.4 如何改进

- 右键增加“轻触”判定：短时间内拇指-中指距离必须明显缩小，静止贴合不触发；
- 静止贴合时不再进入右键分支，滚动不被抢；
- 滚动死区从 0.035 降到 0.02，每格距离从 0.22 降到 0.15；
- Windows 滚轮改为直接发送 `amount * 120`，每帧最多 3 格；
- 增加“静止拇指不右键”“拇指贴中指时滚动仍工作”“wheel 单位”测试。

### 5.5 结果

20 个测试通过；用户确认滚动可用，右键误触未再反馈。新的问题是光标卡顿和
关闭按钮左键无反应，进入迭代三。

**产品表达**：区分“拇指自然搭在中指上”和“有意轻触右键”；同时修复了 Windows
滚轮单位问题——这是很多手势鼠标“看起来触发了但没效果”的隐藏坑。

## 六、迭代三（v1.1.2）：解决冻结与左键可靠性

### 6.1 为什么迭代

用户反馈光标有时停在某个区域不动，过一会才恢复；移动到关闭按钮等位置后左键
有时没反应。这两个问题会直接让用户放弃使用。

### 6.2 用户体验

- 光标停在某个区域，手势暂时失效；
- 瞄准关闭按钮、捏合、松开，窗口没有关闭；
- 不确定是手势识别失败，还是鼠标事件没发出。

### 6.3 根因

1. 右键锁存没有超时：拇指持续靠近中指时，每帧提前返回，光标被无限期冻结；
2. 捏合→拖拽只看时间：按住超过 0.3 秒就进入拖拽，即使完全没移动；松开时
   既不是拖拽也不是点击，慢点击关闭按钮就“没反应”；
3. 光标映射可以到达屏幕物理角落；PyAutoGUI failsafe 抛异常后被吞掉，但光标
   仍停在角落，后续移动继续被拦截，表现为卡死。

### 6.4 如何改进

- 右键锁存增加 0.80 秒超时，超时后恢复光标/捏合/滚动仲裁；
- 拖拽必须同时满足“按住超过 0.3 秒”和“移动超过 0.15 手掌宽”；
- 静止长按松开算点击，不再因为时间超过 0.3 秒而丢失；
- 光标与屏幕四角保持 8 px，避免误触 failsafe；
- `MouseController.failsafe_triggered` + 主循环检查：真触发 failsafe 时干净退出，
  不再把光标留在角落；
- 增加锁存超时、静止长按点击、映射避开角落测试。

### 6.5 结果

23 个测试通过。用户验收核心功能，确认右键、滚动、卡顿和关闭按钮问题基本解决；
仍有轻微卡顿，初步判断来自相机延迟，进入产品化 backlog。

**产品表达**：手势鼠标不只要“识别得到”，还要“随时能退出”；锁存超时、静止
长按点击、屏幕边界保护，都是把 demo 变成可用产品必须处理的细节。

## 七、迭代四（v1.1.3）：双击，不新增手型

### 7.1 为什么迭代

完整鼠标词汇需要双击。但新增一个独立手势会增加学习成本和冲突风险，因此要先
回答：双击应该设计成什么手势，才能和单击、拖拽、右键、滚动共存？

### 7.2 方案比较

| 方案 | 手势 | 冲突 | 自然度 | 风险 |
|---|---|---|---|---|
| **双捏合（采用）** | 拇指-食指快速捏合两次 | 与左键同姿势，靠 click 间隔区分；符合鼠标语义 | 高 | 受系统双击时间限制 |
| 拇指-小指轻触（备用） | 碰小指一次 → 直接 `doubleClick()` | 基本无冲突 | 很低 | 小指更不灵活、跟踪需验证 |
| 食指+中指双击 | 两指快速点两下 | 与滚动冲突 | 中 | 滚动被误触发 |
| 拇指+中指双击 | 拇指碰中指两次 | 与右键冲突 | 中 | 右键 tap/latch 会抢 |
| 空中食指双击 | 食指快速下压两次 | 与光标移动冲突 | 低 | 容易误触 |

结论：选 **双捏合**。它不是新手势，而是把“左键单击”在时间上组合两次，和物理
鼠标双击完全一致，学习成本最低。

### 7.3 用户体验

第一版实现后，用户反馈“双击有些难以触发”。原因是应用层比系统更严：

- 要求每次捏合 ≤0.3 秒；
- 光标位移限制 8 px；
- 两次 click 必须在 0.5 秒内。

### 7.4 如何改进

- 移除“单次捏合 ≤0.3 秒”的门槛：只看两次 click 的间隔和光标位移；
- 光标位移上限从 8 px 放宽到 16 px，第二次点击前吸回第一次位置；
- 读取 Windows `GetDoubleClickTime()`，取系统时间与配置中更严格的值；
- `CLICK_DEBOUNCE` 从 0.30 降到 0.10，避免第二次点击被防抖吃掉；
- 左键后 0.30 秒内抑制右键候选，防止拇指回到中指抢走第二次点击；
- 不调用 `pyautogui.doubleClick()`，避免第一次已发出后变成三次点击；
- 增加单击、双捏合、超时、位移过大、长按第一下、右键抑制测试。

### 7.5 结果

29 个测试通过。双击已实现，阈值已放宽，等待用户最终确认真机双击打开是否稳定。
如果仍难触发，备选方案是“拇指-小指轻触 → 直接 doubleClick”（无名指已分配给
音量手势，不能再占用）。

**产品表达**：双击 = 两次捏合，和物理鼠标语义一致，不新增手型；真正难点不是
“识别两次”，而是让应用窗口和 Windows 双击语义对齐。

## 八、迭代五（v1.1.4）：音量控制，不占用现有指对

### 8.1 为什么迭代

演示/教学中经常需要调节音量，但手势鼠标此前只能控制光标，音量还要另一只手去
按键盘。用户明确提出需要“不离开手势模式”的音量控制。

### 8.2 手势选择

采用 **拇指 + 无名指捏合，然后上下移动手**：

- 无名指此前没有参与任何手势，和单击/双击（拇指-食指）、右键（拇指-中指）、
  滚动（食指+中指）都不冲突；
- 上下移动复用滚动的手掌中心位移模型，学习成本低；
- 代价是无名指不够灵活，MediaPipe 对无名指指尖的跟踪需要实测。

### 8.3 冲突与安全设计

- 先分开拇指/无名指（`d_tr > VOLUME_EXIT_RATIO`）再捏合，避免自然握拳
  误入音量模式；
- 无名指必须比食指/中指更靠近拇指，否则仍按原手势处理；
- 音量候选优先于右键，避免拇指-中指距离较近时抢走无名指手势；
- 上移手 = 音量增大，下移 = 音量减小；每帧最多 2 步；
- 松开无名指或手消失即退出音量模式。

### 8.4 如何改进

- 新增 `volume_controller.py`，Windows 使用 `VK_VOLUME_UP/DOWN` 媒体键；
- `GestureController` 增加可选 `volume=` 依赖和 `STATE_VOLUME`；
- `main.py` 注入音量控制器，启动 banner 增加音量手势；
- 新配置：`VOLUME_ENTER_RATIO`、`VOLUME_EXIT_RATIO`、
  `VOLUME_DEAD_ZONE_RATIO`、`VOLUME_PALM_PER_STEP`、
  `VOLUME_MAX_STEPS_PER_FRAME`、`VOLUME_CONFIRM_FRAMES`；
- 新增音量武装、上下移动、退出、每帧限幅和媒体键封装测试。

### 8.5 结果

35 个测试通过（27 手势 + 5 鼠标安全 + 3 音量键）。音量手势已实现，等待用户
真机确认无名指捏合是否舒适、音量是否实际变化。

**产品表达**：把未使用的无名指变成音量控制；先分离再捏合、只认最靠近拇指的
指对，避免和点击/右键/滚动互相抢。

## 九、迭代六（v1.1.5）：安全角释放 + 真实分辨率映射

这一轮不是新增手势，而是组员代码评审发现的两个**集成层缺陷**：一个会让左键
卡在按下状态，一个会让光标映射偏移。两项都在 v1.1.5 修复，并补了回归测试。

### 9.1 为什么把两项放在同一迭代

两项问题都发生在“手势识别之外”：

- 第一项发生在 PyAutoGUI 安全角与鼠标按键释放之间；
- 第二项发生在摄像头实际输出尺寸与光标坐标映射之间。

它们不影响 MediaPipe 识别本身，但都会让用户觉得“手势不准/程序卡住”。因此
作为同一轮稳定性修复处理，统一验证“退出是否干净”和“坐标是否对齐”。

### 9.2 改进一：安全角触发时强制释放左键

#### 9.2.1 用户看到的现象

- 拖拽文件/选中文本时，把鼠标甩到屏幕角落触发 PyAutoGUI failsafe；
- 程序退出或光标恢复后，左键仍处于按下状态；
- 之后再点击、拖拽会表现异常，严重时像“鼠标一直在拖东西”。

这是一个隐蔽但高影响的问题：用户以为程序已经退出，实际上系统仍认为左键按着。

#### 9.2.2 根因

原实现中：

```python
def mouse_up(self):
    self._safe(pyautogui.mouseUp, _pause=False)
```

`_safe()` 会捕获 `pyautogui.FailSafeException` 并设置 `failsafe_triggered`，但
**`mouseUp()` 自己也会执行 failsafe 检查**。当光标仍在角落时：

1. `mouseUp()` 抛 `FailSafeException`；
2. `_safe()` 捕获并吞掉；
3. 按键实际上没有释放；
4. `main.py` 的 `finally` 再次调用 `mouse_up()`，仍然被同一个检查拦住。

所以“捕获异常”不等于“释放按键”。这是原实现真正的 bug。

#### 9.2.3 改动

在 [mouse_controller.py](mouse_controller.py) 增加一个只用于释放按键的安全路径：

```python
def _release_button(self, button):
    old = pyautogui.FAILSAFE
    pyautogui.FAILSAFE = False
    try:
        pyautogui.mouseUp(button=button, _pause=False)
    finally:
        pyautogui.FAILSAFE = old

def release_all(self):
    for button in ("left", "right"):
        self._release_button(button)
```

配套修改：

- `mouse_up()` 改为走 `_release_button("left")`，不再经过 `_safe()`；
- [main.py](main.py) 的 `finally` 改为先调 `release_all()`，失败再兜底 `mouse_up()`；
- 只有“释放按键”这一小段临时关闭 failsafe，释放后立即恢复，不是全局关闭；
- 同时释放 left/right，避免拖拽/右键状态残留。

#### 9.2.4 验证

新增 `test_release_all_bypasses_failsafe`：

- 在 `FAILSAFE=True` 时调用 `release_all()`；
- 断言 `mouseUp` 分别以 `button="left"` 和 `button="right"` 被调用；
- 断言调用后 `pyautogui.FAILSAFE` 恢复为 `True`。

这保证了“即使光标在角落，释放调用也会真正到达 PyAutoGUI”，同时不破坏后续
安全角保护。

#### 9.2.5 边界

- 如果进程被强制杀死（任务管理器结束进程），`finally` 不会执行，任何应用都
  无法保证释放；这是操作系统层面的边界。
- `release_all()` 是 best-effort：单个按键释放失败会被捕获，继续尝试另一个键。
- 正常拖拽结束仍然走 `mouse_up()`，只是它现在也具备 failsafe 逃生能力。

### 9.3 改进二：用相机第一帧的真实分辨率做映射

#### 9.3.1 用户看到的现象

- `config.py` 请求 640×480，但相机实际输出 1280×720；
- 光标在画面中间时还能用，越往边缘越偏，或者手还没到画面边缘光标就贴边；
- HUD 的活动区域矩形和真实画面比例对不上；
- 手离开“规定区域”后光标贴边，看起来像卡住。

#### 9.3.2 根因

原 `main.py` 用配置值构造控制器：

```python
controller = GestureController(mouse, config.CAMERA_WIDTH, config.CAMERA_HEIGHT)
```

但 `cap.set(CAP_PROP_FRAME_WIDTH/HEIGHT, ...)` 只是**请求**，很多摄像头会忽略，
返回 1280×720、640×360 或其他尺寸。`HandTracker` 返回的是**实际帧像素坐标**，
而 `GestureController` 仍按 640×480 做 `np.interp`，于是：

- 活动区域边界按错误尺寸计算；
- 光标映射被压缩/偏移；
- `FRAME_REDUCTION=100` 在大分辨率下比例变小，在小分辨率下比例变大。

#### 9.3.3 为什么“归一化”不能替代真实分辨率

这是评审里最关键的一点：

| 机制 | 解决什么 | 不能解决什么 |
|---|---|---|
| 手掌尺寸归一化 | 手势距离阈值随手距/分辨率变化 | 像素坐标 → 屏幕坐标的映射 |
| 实际 `frame.shape` | 活动区域和光标映射的像素基准 | 手势距离的尺度变化 |

归一化让 `d_ti/palm` 在 640×480 和 1280×720 下含义一致，但 `_map_to_screen()`
仍然需要知道“画面宽度是多少像素”。两者必须同时存在，不是二选一。

#### 9.3.4 改动

[main.py](main.py) 在打开相机后先读第一帧：

```python
ok, first_frame = cap.read()
cam_h, cam_w = first_frame.shape[:2]
controller = GestureController(mouse, cam_w, cam_h, volume=volume)
```

同时：

- `print_intro()` 同时显示**实际分辨率**和**请求分辨率**，例如
  `1280 x 720 (requested 640 x 480)`；
- `GestureController` 按实际分辨率计算活动区域；
- `FRAME_REDUCTION` 不再固定为像素，而是从配置参考分辨率缩放到实际分辨率：

```text
fr_x = FRAME_REDUCTION * actual_width  / CAMERA_WIDTH
fr_y = FRAME_REDUCTION * actual_height / CAMERA_HEIGHT
```

例如 640×480 下 `FRAME_REDUCTION=100`，实际 1280×720 时变为约 200/150 px，
保持相同的相对活动区域，而不是让死区比例随分辨率漂移。

- HUD 的 `active_area` 改为使用 `controller.active_area()`，不再自己按配置值算；
- 第一帧直接送入主循环，不丢帧，也不重复读取。

#### 9.3.5 验证与边界

新增 `test_active_area_scales_with_actual_resolution`：

- 用 1280×720 构造控制器；
- 断言活动区域为 `(200, 150, 1080, 570)`，证明 640×480 的 100 px 参考值
  被正确缩放。

另外用 1280×720 假摄像头跑通完整 `main.py` 主循环，banner 正确打印
`1280 x 720 (requested 640 x 480)`。

边界：

- 如果相机在运行中切换分辨率，控制器不会自动重建；需要重启应用。
- 相机可能做裁剪/旋转，`frame.shape` 只能解决尺寸，不解决画面方向。
- DPI 缩放/多显示器仍属于独立的屏幕坐标问题，不在这一轮范围内。

### 9.4 顺带补上的边界：`Out of Area`

活动区域外的旧行为是 `np.interp` 把坐标压到屏幕边缘，用户会看到“光标贴边
不动”。v1.1.5 改为：

- 食指离开活动矩形时，光标保持最后位置；
- HUD 显示 `Out of Area`；
- 手回到活动区域后继续移动。

这不是新的手势，而是让“活动区域边界”变成可解释的状态，避免被误认为死机。

### 9.5 两项改进后的行为对比

| 场景 | v1.1.4 及以前 | v1.1.5 |
|---|---|---|
| 拖拽中触发安全角 | 可能残留左键按下 | `release_all()` 强制释放并恢复 failsafe |
| 相机忽略请求分辨率 | 光标映射压缩/偏移，活动区不准 | 用第一帧真实尺寸构造控制器 |
| 1280×720 下的 100 px 死区 | 比例变小，活动区偏移 | 缩放为约 200/150 px，保持相对比例 |
| HUD 活动区域 | 按配置值画，可能与画面对不上 | 按控制器真实矩形画 |
| 手出活动区域 | 光标压到屏幕边缘 | 保持最后位置，显示 `Out of Area` |
| 退出清理 | `mouse_up()` 可能被 failsafe 拦截 | `finally` 调 `release_all()` |

### 9.6 真机验收清单

建议按下面顺序验，避免把“手势识别问题”和“集成问题”混在一起：

1. **安全角释放**
   - 打开一个文本编辑器，按住左键拖选一段文字；
   - 保持拖拽，把鼠标甩到屏幕角落触发 failsafe；
   - 程序退出后，在编辑器里单击/拖动，确认左键没有处于按下状态。
2. **实际分辨率**
   - 看启动 banner 的 `Camera resolution` 实际值；
   - 手分别移动到画面四个角，确认光标能到对应屏幕边缘；
   - 确认 HUD 活动矩形与手实际能控制的范围一致。
3. **活动区域外**
   - 手移出活动矩形，确认 HUD 显示 `Out of Area`，光标不跳边缘；
   - 手移回，确认光标继续跟手。
4. **回归**
   - 单击、双击、拖拽、右键、滚动、音量各做一次；
   - 确认这次改动没有改变原有手势行为。

### 9.7 结果与产品表达

- 38 个测试通过（29 手势 + 6 鼠标安全 + 3 音量键）；
- 1280×720 假摄像头主循环冒烟通过；
- 安全角释放、真实分辨率、活动区外保持均有回归测试；
- **待用户真机确认**：安全角后左键是否真的松开、实际分辨率下光标是否不再偏移。

**产品表达**：

> 手势识别正确，不代表产品可靠。安全角必须“先释放按键再退出”，否则会出现
> “光标回来了但左键还按着”的隐蔽故障；归一化解决手势尺度，真实分辨率解决
> 坐标映射，两者缺一不可。

## 十三、产品介绍建议

### 一句话

用普通摄像头把手指动作变成鼠标和系统控制，本地运行、无需额外硬件。

### 目标用户

优先选择一个主场景：**演示/教学** 或 **无障碍/无接触操作**。不要同时宣称所有人
都能用；当前尚未做用户研究。

### 差异化

- 手掌尺寸归一化，换手距/分辨率不漂移；
- 右键区分“静止贴合”和“有意轻触”；
- 滚动小数累加 + Windows wheel 单位修复；
- 双击与物理鼠标语义一致，不新增手型；
- 音量用拇指+无名指捏合后上下移动，不占用现有指对；
- 按真实相机分辨率映射，failsafe 强制释放按键；
- 锁存超时、边界保护，避免“卡死”；
- 原始版本可回滚，38 个自动化测试。

### 演示流程

启动 → 移动 → 单击 → 双击 → 拖拽 → 右键轻触 → 两指滚动 → 音量。

### 建议补充的指标

- 端到端延迟 p50/p95、实际 FPS；
- 每种手势成功率/误触率；
- 单击/双击成功率；
- 音量手势成功率/误触率；
- 3–5 人 SUS/主观评分。

### 路线图

现场校准 → DPI/多屏 → 场景手势包 → 托盘/打包 → 用户测试。
